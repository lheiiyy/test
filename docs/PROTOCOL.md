# Pairing Protocol — DroidBridge

## Why this exists

The reference video's pairing flow (VIDEO_ANALYSIS.md §1, frames 010–029) is:
phone scans a QR code shown in a PC browser tab → terminal reports a new
`adb`-over-Wi-Fi session. The video never shows what's actually *encoded* in
that QR code, or whether any authorization step happens beyond "same LAN,
scan code" (VIDEO_ANALYSIS.md §3, "Cannot be determined"). Rather than guess
at an unknown wire format, DroidBridge defines its own — one designed so that
the QR code itself can never be sufficient to gain access, because the real
authorization is always Android's own on-device dialog.

## Design constraints

1. **No permanent credentials in the QR code.** The payload carries a
   session lookup key, not a password or long-lived token.
2. **Short-lived.** A payload is only valid for `PAIRING_SESSION_TTL_MS`
   (2 minutes) from issuance.
3. **Single-use.** Once a session is consumed (successfully matched), a
   second attempt with the same `sessionId` is rejected even if it hasn't
   expired yet — this is enforced by `PairingService`, not by the payload
   schema itself (a schema can't express "not already used").
4. **Structural validation before anything else.** Malformed input is
   rejected before any session lookup happens, so a garbage QR code (or a
   QR code from something that isn't DroidBridge at all) fails fast and
   distinctly from "wrong/expired session."
5. **Cannot bypass Android's own consent.** Successfully validating and
   consuming a payload only tells DroidBridge "attempt a pairing handshake
   with this endpoint" — it still results in `adb pair`/`adb connect`,
   which still requires the phone's own "Allow wireless debugging" /
   "Allow USB debugging" dialog to be tapped by whoever is holding the
   phone. There is no field in this payload, and no code path in
   `PairingService` or `AdbService`, that can answer that dialog on the
   phone's behalf.

## Wire format

```ts
interface PairingPayload {
  version: 1;
  sessionId: string;   // UUID v4, generated by the desktop app per session
  endpoint: string;    // "<ipv4>:<port>" the desktop app's pairing listener is on
  token: string;       // 32-byte random hex — a lookup key, not a credential
  expiresAt: number;   // Unix ms; payload MUST be rejected once Date.now() > this
}
```

Defined in `shared/src/protocol/pairing.ts` as a `zod` schema
(`pairingPayloadSchema`), `.strict()` so unknown extra fields cause rejection
rather than being silently ignored — an important property for a payload
that's about to be trusted enough to attempt a device connection.

### Why a `token` if it's "not a credential"

It distinguishes "I have the exact QR code DroidBridge generated for this
session" from "I guessed a valid-looking UUID." It's short-lived and
single-use like the rest of the payload, so its compromise window is the
same 2 minutes as everything else — it is not stored anywhere long-term, and
`Logger`'s redaction list explicitly strips any field literally named
`token` from log output as a second line of defense.

### Why `endpoint` is in the payload at all

In a later phase, when DroidBridge runs a local pairing listener (the
GUI equivalent of the reference's browser-hosted QR page — see
`UI_SPEC.md` "Screen: Pairing"), the phone needs to know where to report
back to on the LAN. For Phase 2, `PairingService.createSession(endpoint)`
takes this as a caller-supplied string since no listener exists yet to
generate it automatically — see `ARCHITECTURE.md`'s "Phase 2 scope" notes.

## Validation pipeline

`validatePairingPayload(raw, now)` (`shared/src/protocol/pairing.ts`):

1. If `raw` is a string (the literal scanned QR content), `JSON.parse` it.
   A parse failure → `{ ok: false, reason: 'malformed' }`.
2. Run the zod schema. A version mismatch is reported as its own reason
   (`unsupported-version`) distinct from other structural failures
   (`malformed`), so the UI can say "update DroidBridge" instead of a
   generic "bad QR code."
3. Check `expiresAt` against `now` (injectable for tests) →
   `{ ok: false, reason: 'expired' }` if past.
4. Otherwise `{ ok: true, payload }`.

`PairingService.consume(raw)` (`desktop/src/main/services/pairing/PairingService.ts`)
wraps this with the session-lifecycle checks the schema can't express:

5. Look up `payload.sessionId` among sessions this `PairingService` instance
   itself issued → unknown session (never issued by us, or already swept)
   → `{ ok: false, reason: 'unknown-session' }`.
6. Compare `payload.token` against the stored session's token → mismatch
   (right ID, wrong/forged token) → also `unknown-session`, deliberately not
   a more specific "token mismatch" message, so an attacker probing session
   IDs can't distinguish "doesn't exist" from "exists, wrong token."
7. Check `consumed` flag → already used → `{ ok: false, reason: 'already-used' }`.
8. Mark `consumed = true` and return `{ ok: true, payload }`.

`sweepExpired()` removes consumed/expired sessions from memory so the map
can't grow unbounded across a long-running desktop session; it's not
security-critical (expired/consumed sessions are already rejected by steps
3/7 above regardless of whether they've been swept yet).

## Explicitly rejected inputs (see `shared/src/protocol/pairing.test.ts`)

- Malformed JSON
- Valid JSON missing a required field
- An unsupported/future `version`
- An expired `expiresAt`
- A non-IPv4-host:port `endpoint`
- A payload with extra/unknown fields (schema is `.strict()`)
- A payload for a session this instance never issued
- A payload with a valid session ID but a forged `token`
- A payload whose session was already consumed once

## What this protocol deliberately does not do

It does not implement the reference's unnamed/unlabeled "Generate QR
Payload" menu item (#38) — see `FEATURE_SPEC.md` for why that item is
omitted entirely rather than guessed at. This protocol only covers
*device pairing* QR content; it is not a general-purpose "QR payload"
mechanism for arbitrary commands, which is exactly the kind of ambiguous,
unverifiable feature this project's brief says not to build from a source
that never shows it executing.
